# Контекст проекта SFRPFR

Единый продуктовый контекст для владельца, Cursor и разработчиков.  
Технические детали — в `docs/specs/`, `docs/architecture.md`, `KODA.md`.  
Секреты и ПДн в этот файл не писать.

## 1. Назначение

**SFRPFR** (бренд: ПроверкаСтажа / `proverkastaza.ru`) — платформа для первичной оценки оснований, подготовки документов и сопровождения обращений граждан по вопросам стажа и пенсии.

Система **не** обещает гарантированный перерасчёт и **не** подаёт заявления вместо клиента.  
Канон подачи: [`scripts/assets/copy/submission-position.md`](../scripts/assets/copy/submission-position.md).

Публичные цены поэтапно: **3 000 / 5 000 / 8 000 ₽** (`DIAG` → `DOCS` → `SUPPORT`).

## 2. Проблема

Клиенту сложно понять, есть ли расхождения в учёте стажа, собрать документы и видеть понятный статус.  
Специалисту сложно видеть файлы рядом с OCR, подтверждать рукописные трудовые и вовремя запускать следующий шаг воронки.

Целевой измеримый сценарий:

> Клиент оставил заявку → загрузил документы → получил понятный статус → специалист увидел дело, файлы и распознавание → при сомнениях проверил (особенно трудовую) → ИИ сделал анализ расхождений → клиент получил **бесплатное краткое резюме** → система предложила 3 000 → затем 5 000 → затем 8 000.

## 3. Роли

| Роль | Действия |
|------|----------|
| Клиент | заявка, согласие, загрузка документов, статусы, бесплатное резюме, выбор тарифа, оплата, подача в СФР/Госуслуги сам |
| Специалист | очередь дел, файлы, OCR/HITL, правка полей, подтверждение, запуск анализа, утверждение резюме/PDF |
| ИИ / OCR | распознавание, классификация, черновик расхождений и резюме по шаблону; **не** юридическое решение |
| Руководитель | роли, воронка, качество, интеграции |

Связка с уже существующими колонками ТЗ-33 и тарифами:

## 6. Известные разрывы (почему «загрузил — и тишина»)

1. Клиент часто видит общий статус дела, но **не** ясный путь «файл принят → OCR → проверка → резюме готово».
2. Специалист может не попасть в очередь HITL / не видеть оригинал+OCR рядом, если ingest не проставил `ingest_review_required` или байты OCR не резолвятся (см. gap ТЗ-13a: worker читал Storage, а SoT — local/Disk).
3. Classify/analyze может стартовать до подтверждения трудовой.
4. Бесплатное краткое резюме **до** оплаты DIAG ещё не закреплено как обязательный продуктовый гейт (сейчас акцент на платной диагностике 3 000 ₽).
5. amoCRM не должна участвовать в этом контуре.

Подробное ТЗ закрытия разрывов: [`specs/35-ai-document-intake-and-free-summary.md`](specs/35-ai-document-intake-and-free-summary.md).

## 7. Что нельзя

- Обещать перерасчёт / сумму / «СФР обязан».
- Подавать заявления от имени клиента.
- Писать ПДн, токены, сканы в Git.
- Тянуть amoCRM в OCR/воронку документов.
- Отдавать клиенту сырой OCR / внутренние confidence / черновые гипотезы без шаблона.

## 8. Правило разработки

Одна задача = один проверяемый пользовательский результат.  
Крупные изменения воронки/OCR — сначала план (KODA), затем узкий PR.  
Перед кодом — сверка с ТЗ-13/13a/32/33/35 и позицией о подаче.
