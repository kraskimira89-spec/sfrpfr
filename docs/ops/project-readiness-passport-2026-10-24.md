## 1. Вердикт

Основной каркас MVP **реализован** и отмечен ✅ в `docs/ops-mvp-checklist.md`.
Готовность бизнеса к **потоку** клиентов **не равна** галочкам чек-листа и **не равна** завершению SFRFR-93.

Единого свежего сквозного E2E «заявка → … → результат» **нет**. Живой полный проход **сегодня не повторялся**.

### 1.1. Экспертные оценки (не метрики приёмки)

| Оценка | Диапазон | Основание | Ограничения |
|---|---|---|---|
| Реализовано (каркас MVP) | ≈ 85–90% | 6/6 направлений в чек-листе = ✅; открыты хвосты MAX funnel R1, ingest E2E, Postbox | Экспертная шкала ревьюера; **не** измеряемый KPI |
| Проверено в проде (сквозной путь) | ≈ 45–55% | фрагменты battle/smoke; lead/каналы E2E пустые; C1 не принят | Нет единой методики %; **не** критерий приёмки |

**Запрет:** не использовать эти проценты как критерий «принято / готово к потоку».

## 4. Блокер: дубль чека на 8000 ₽

### 4.1. Что случилось

| Поле | Значение |
|---|---|
| Задача | [SFRFR-89](https://tracker.yandex.ru/SFRFR-89) (в работе; deadline 2026-10-28) |
| Инцидент | боевой SUPPORT 8000 ₽, 2026-10-23 |
| Что названо дублем | **два самостоятельных** succeeded чека **`type=payment`** на **один** платёж (не пара payment+refund; не повтор notify) |
| Причина | **установлена:** webhook/`ensure_payment_receipt` создавал второй чек, пока registration ещё `pending`/отставал, при уже ушедшем авточеке из invoice (`create_payment` без settlements + ensure со settlements) |
| Связь с SFRFR-93 (fiscal reconcile) | **не установлена** как причина дубля; reconcile закрывает хвост `canceled` после paid. **Стоп-условие наблюдения 93 по этому инциденту — нет** |
| Доказательства | `docs/history/2026-10-23-battle-support-8000.md`; `docs/history/2026-10-23-receipt-dedup-ensure-gate.md`; фикс gate #226 — `docs/history/2026-10-23-smoke-dedup-226-1rub.md` |

| Факт | Статус | Доказательство |
|---|---|---|

### 4.3. Временное ограничение и критерий повторной приёмки

**Ограничение:** новый боевой платёж (полная сумма / воспроизведение дубля) — **только** по отдельному согласованию владельца. Без согласования — не проводить.

**Критерий повторной приёмки 8000 (пакет):**

1. На одном платеже ровно **один** succeeded `type=payment` (и нет второго succeeded payment).
2. Статус плана кассы не хуже согласованного (минимум закрыт инцидентный паттерн ensure; желательно `BLOCKER_CLEARED` или явное принятие остаточного риска гонки — SFRFR-94).
3. Отдельное «да, платим 8000» владельца.
4. Успешные 3000/5000 **не** засчитывать вместо п.1–3.

## 7. Решения владельца (пакет)

См. полный список: [`owner-decisions-pack-2026-10-24.md`](./owner-decisions-pack-2026-10-24.md)

Кратко:

1. Принять или отклонить сквозной E2E-протокол после прогона.
2. Утвердить коммерческие условия (услуги, цены 3/5/8, состав, сроки, граница автомат↔эксперт, споры/возвраты).
3. Назначить операционные роли (заявки, документы, клиент, оплаты/чеки, инциденты).
4. Согласовать любые реальные платежи / возвраты (в т.ч. пополнение ЮKassa для refund 8000).
5. SFRFR-93: до конца окна наблюдения отдельных действий не требуется; закрытие — по критериям задачи, не по `candidates=0` alone.

## 8. Порядок следующих крупных работ

1. **Документация (этот PR):** паспорт + блокеры + пакет решений + E2E-протокол — точка отсчёта SFRFR-100.
2. **Касса / 8000:** без нового боевого платежа — сверка доказательств; возврат денег — после пополнения баланса ЮKassa; повторная приёмка 8000 — только с «да, платим».
3. **Сквозная приёмка:** заполнить протокол `e2e-client-path-acceptance-protocol.md` на тестовом деле (без лишних ПДн).
4. **SFRFR-93:** продолжать наблюдение до согласованного срока **отдельно**; стоп только при своих stop-условиях (не из дубля 8000).
5. **MAX funnel critical / коммерция:** после или параллельно приёмке пути — по решению Стратега.
