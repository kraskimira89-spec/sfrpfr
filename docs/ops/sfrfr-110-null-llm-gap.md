# Зарегистрированный пробел: Null → LLM

## Формулировка покрытия (узкая)

> Политический E05/F04-путь проверен изолированно. Запрет неподтверждённых
> утверждений во всех MAX-ответах не доказан.

## Воспроизведение

```text
Нет доверенного контекста (NullTrustedErrorContextAdapter)
→ обычный LLM-путь (action=max_llm_reply)
→ модель предлагает «исправлено»
→ зафиксировано фактическое поведение конечного отправляемого ответа
```

Тест: `tests/unit/test_max_e05_f04_wire_path.py::test_null_adapter_no_error_admission_falls_through_to_llm_path`

Фактическое поведение (на head wire): invented «исправлено» **может уйти**
клиенту. Защита — prompt/`CLIENT_CHAT_SYSTEM`, не handler-gate.

## Что не требуется

Блокировать все ответы при отсутствии фактов.

## Что требуется отдельно (не смешивать с E01 audit)

Определить ограничение утверждений о **выполненных действиях** на `max_llm_reply`
(пост-фильтр критических маркеров / политика). Отдельная узкая задача SFRFR-110.

## Связь с доставкой policy

| Ситуация | Смысл |
|---|---|
| `enqueue_failed` | Гарантированный отказ **до** записи outbox; handler шлёт тот же policy-текст напрямую один раз |
| `enqueued_pending` / transport без persist | Подготовка есть; полный исход доставки не подтверждён |
| `UNKNOWN_AFTER_ACCEPT` (outbox guards) | Транспорт мог принять, запись статуса потеряна — **не** слепой retry; ≠ `enqueue_failed` |

Согласованность текста при `enqueue_failed` ≠ доказательство отсутствия дубля
при неизвестном исходе после возможной записи.
