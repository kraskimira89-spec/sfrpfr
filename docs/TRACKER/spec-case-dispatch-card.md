# Спека: карточка пенсионного дела в Яндекс Трекере (диспетчерская)

**Дата:** 2026-10-25  
**Статус:** аудит выполнен · очередь дел **не создана** · production-хуки **не включались**  
**Задача:** [SFRFR-118](https://tracker.yandex.ru/SFRFR-118)  
**Связь с UI:** 13 ступеней admin — `apps/admin/src/lib/case-funnel-types.ts`  
**Канон ПДн:** без ФИО/телефона/СНИЛС/ИЛС/платёжных секретов в Трекере

## Принцип разделения

> Кабинет и БД хранят подтверждённые факты дела. Трекер организует работу сотрудников. MAX/email доставляют клиенту сообщения. Фоновый планировщик следит, чтобы события не потерялись.

Трекер **не** является единственным хранилищем документов, подтверждений оплаты и таймеров клиентских напоминаний.

| Сведения | Основное хранилище | В Трекере |
|---|---|---|
| Контакты и согласия | БД | минимум + `case_ref` + статус согласий |
| Оригиналы документов | закрытое хранилище | тип, статус, ссылка **в кабинет** (не прямой файл) |
| OCR / периоды | БД / артефакты | готовность, проблема |
| Находки и резюме | версионированный результат | краткий итог, версия |
| Заказы и оплаты | платёжный контур + БД | статус **конкретной** услуги |
| Обращения DOCX/PDF | закрытое хранилище | реестр + статус передачи |
| Подтверждение подачи | БД + доказательство | дата, адресат, следующий срок |
| Задачи специалиста | Трекер ↔ БД | исполнитель, дедлайн, результат |
| Расписание сообщений клиенту | планировщик приложения + outbox | ближайшее действие (сводка) |
| История событий | журнал приложения | значимые события без шума |

## 1. Аудит существующей интеграции (факт на 2026-10-25)

### 1.1. Очереди в org (live API)

| Ключ | Назначение сейчас | Подходит для карточки дела? |
|---|---|---|
| `TRACKER` | org workspace | нет |
| `SFRFR` | продукт / infra / agents | нет (не смешивать с клиентскими делами) |
| `STAZH` | качество, SLA, улучшения из admin | **нет** как родитель дела; остаётся для инцидентов |
| `FUNNEL` | ops воронки **без** карточек клиентов | **нет** (процессные задачи, не диспетчерская) |
| `PUB` | публикации | нет |

**Вывод:** отдельной очереди «одна карточка на пенсионное дело» **нет**. Создавать новую очередь **только после явного решения владельца** (кандидат ключа: `CASE` / `DELO`). Не создавать автоматически скриптом без проверки.

### 1.2. Что уже есть в коде

| Точка | Путь / факт |
|---|---|
| Клиент API | `src/sfrfr/integrations/yandex_tracker/__init__.py` — create issue, PII sanitizer, `case_ref_for` |
| Создание из admin | `quality_issues.py` + `POST /admin/cases/{id}/tracker` → очередь **`TRACKER_QUEUE` (по умолчанию STAZH)** |
| Связь case ↔ issue | таблица `case_tracker_issues` + `cases.tracker_last_issue_key` |
| Типы задач | bug, sla_incident, process_improvement, … — **не** `case_card` |
| Дедуп | одна открытая задача на `(case_ref, issue_type)` |
| Health | `GET /admin/tracker/health` |
| UI admin | модалка «Создать задачу в Tracker» + список `tracker_issues` |
| Плагины Weavix | `plugins/tracker/stazh-quality-wizard`, `sfrfr-issue-wizard` |
| Outbox клиенту | `case_chat_delivery` / MAX path — **не** через Трекер |
| next_action / waiting_on | поля дела в БД + `staff_work_queue` |
| Webhook Трекер → app | **не найден** как рабочий endpoint приёма команд специалиста |
| Авто-карточка на каждое дело | **нет** |
| Синк 13 ступеней в Трекер | **нет** |
| Напоминания 3д клиенту / 5/10/15/30 специалисту из единого планировщика | частично разрозненно (unread reminder, payment reminder, archive_followup); **не** как единый case-dispatch контур |

### 1.3. Что нельзя ломать

- STAZH-поток качества (`create_quality_issue_from_case`) остаётся.
- Не дублировать оплату/доставку из `b2c_status` (см. FunnelFacts / `toFunnelFacts`).
- Не писать ПДн и прямые cabinet/storage URL в issues (уже запрещено санитайзером).

## 2. Целевая модель: одна родительская карточка на дело

```text
Клиентское дело <case_ref>

Ответственный: специалист
Текущий этап: <StageId из 13>
Следующий шаг: …
Срок: …
Ожидаем: сотрудник | клиент | ведомство | оплата
Синхронизация: актуально | ожидает | ошибка
```

- Несколько самостоятельных дел одного человека → **отдельные** карточки.
- Не создавать сразу 13 пустых подзадач. Рабочие задачи — только при реальной работе (см. §3).
- Родитель **не** закрывается автоматически от последней подзадачи или оплаты.

### Связь в БД (предложение поверх существующего)

Расширить модель связей, не ломая STAZH:

```text
case_tracker_links (или расширение case_tracker_issues)
  case_id
  case_ref
  role: parent_case | work_task | quality
  tracker_issue_key
  stage_id?          -- для work_task
  case_revision
  sync_status
  is_open
```

`issue_type=case_card` (или отдельная таблица) — ровно **одна** открытая родительская карточка на дело.

## 3. 13 ступеней → когда создавать задачу специалисту

| Ступень | `StageId` | Задача специалисту |
|---|---|---|
| 1 | `contact_consents` | нет контакта / нет нужного согласия |
| 2 | `documents` | нехватка / качество / конфликт принадлежности |
| 3 | `precheck_summary` | ручная проверка, clarify, согласование резюме |
| 4 | `analysis_payment` | сбой заказа/оплаты; не каждый pending = звонок |
| 5 | `full_analysis` | entitlement granted → назначить работу |
| 6 | `appeals_consent` | обсудить план и объём |
| 7 | `appeals_payment` | ошибка оформления / согласованное сопровождение оплаты |
| 8 | `appeals_documents` | подготовить / проверить / передать пакет |
| 9 | `submission` | help_requested или нет подтверждения подачи |
| 10 | `follow_up` | просрочена обратная связь / срочное уведомление |
| 11 | `response_review` | получен документ для разбора |
| 12 | `escalation_package` | согласован новый маршрут и заказ |
| 13 | `closure` | проверить результат и незакрытые обязательства |

Источник статусов для сводки — `FunnelFacts` / `buildFunnel`, не выдуманный статус Трекера.

## 4. Локальные поля очереди дел (после создания очереди)

Предлагаемый набор (имена — целевые; фактические id — после настройки в UI Трекера):

```text
caseRef                 — непрозрачный идентификатор
currentStage            — StageId (13 значений)
caseRevision            — версия состояния дела
nextAction              — текст следующего шага
nextActionAt            — срок
waitingOn               — staff | client | agency | payment
lastClientResponseAt
submissionConfirmedAt
nextFollowupAt
urgentDeadlineAt
syncStatus              — ok | pending | error
```

Оплаты — **сводка по услугам**, не один флаг «оплачено»:

```text
Анализ: not_ordered | pending | paid | …
Обращения (5k): …
Доп. пакет (8k): …
```

Канон сумм: DIAG / ACCOMP×5000 / ACCOMP×8000 — как в `toFunnelFacts`.

## 5. События, outbox, хуки

```text
Документ / оплата / ответ клиента / действие сотрудника
                         ↓
              Проверка и запись в БД
                         ↓
           Долговременное событие + outbox
                 ↙                    ↘
       Синхронизация Трекера      MAX / email
                 ↓                    ↓
         Задача сотруднику       Сообщение клиенту
```

Примеры `event_type` (идемпотентный `event_id`):

```text
documents_received
precheck_completed
client_question_answered
payment_confirmed
analysis_delivered
appeals_approved
submission_confirmed
agency_response_received
followup_due
call_required
case_closed
```

### Надёжность

1. Событие фиксируется с бизнес-изменением или восстанавливается сверкой.
2. Повтор события → та же задача / то же сообщение (dedup по `event_id` / открытому work_task).
3. Ошибка Трекера **не** откатывает оплату.
4. Ошибка MAX **не** стирает результат анализа.
5. Таймаут create → сверка по `case_ref` + summary, не слепой retry create.
6. Периодический reconcile восстанавливает `sync_status=error`.

### Входящие команды из Трекера (этап позже)

Допустимо: назначить ответственного, сдвинуть срок, результат звонка, запросить проверку напоминания, закрыть work_task с результатом.

**Нельзя** подтверждать одним статусом Трекера: оплату, отправку, подачу, юридический итог, «исправление даты» без источника.

Защита от циклов: origin (`app` | `tracker`), `command_id`, проверка `case_revision`.

Webhook-получатель обязан быть идемпотентным (повторы HTTP у автодействий Трекера).

Документация Яндекса: [локальные поля](https://yandex.ru/support/tracker/ru/local-fields), [автоматизации](https://yandex.ru/support/tracker/ru/automation), [автодействия / повторы](https://yandex.ru/support/tracker/ru/user/create-autoaction), [триггеры](https://yandex.ru/support/tracker/ru/manager/trigger-examples).

## 6. Напоминания

### Клиенту — каждые 3 дня (после подтверждённой подачи)

Планировщик **приложения** (не дублировать расписание в Трекере):

1. Наступил срок.
2. Нет нового ответа / не закрыто / уведомления разрешены.
3. Одно сообщение в outbox.
4. Следующий срок по правилам.

Канал: MAX / email понятным текстом. Технические письма Трекера клиенту **не** слать.

### Специалисту — контрольные дни 5 / 10 / 15 / 30 от подачи

- «Изменений нет» = обратная связь.
- Нет ответа клиента → задача звонка (или повышение приоритета уже открытой).
- После звонка — обязательный результат + следующий шаг.
- Срочный срок из проверенного уведомления > трёхдневного ритма.

Трекер может эскалировать **просроченные work_task** автодействием; клиентский таймер — только в app.

## 7. Контрольные выборки

В кабинете и на доске очереди дел:

- нет ответственного;
- просрочен next step;
- новый документ от клиента;
- оплата подтверждена, работа не начата;
- результат ready, передача не confirmed;
- пакет передан, подача unknown;
- клиент не отвечает;
- ответ ведомства;
- urgent deadline;
- ошибка sync Трекера;
- сообщение не доставлено / исход неизвестен.

Техмонитор: жив ли планировщик, лаг обработки, очередь ошибок, дела без следующего действия.

| Этап | Содержание | Готово? |
|---|---|---|
| **0. Аудит** | этот документ | да |

Код качества STAZH **не** заменять. Новый контур — рядом (`case_card` / новая очередь / отдельный модуль `case_dispatch.py`).

## 9. Чеклист приёмки

1. Двойное событие → одна задача.  
2. Таймаут Трекера → нет дубля.  
3. Оплата сохраняется при недоступном Трекере.  
4. Отказ клиента прекращает ненужные сообщения.  
5. Закрытие дела отменяет запланированные напоминания.  
6. Новый ответ отменяет устаревшее напоминание.  
7. Срочный срок → приоритетная задача.  
8. Изменение в Трекере не создаёт цикл sync.  
9. В комментариях/логах нет лишних ПДн.  
10. Доступ к документам проверяется в кабинете.

## 10. Решение владельца (блокер этапа 1)

Нужен явный выбор:

**Option A.** Новая очередь `CASE` (рекомендуется) — диспетчерская по делам, отдельно от STAZH/FUNNEL/SFRFR.  
**Option B.** Не заводить очередь сейчас — усилить только кабинет + outbox; Трекер оставить для качества/ops.  
**Option C.** Временно пилот на FUNNEL с тегом `case-card` (не рекомендуется: смешение с процессными задачами).

До выбора: **не** создавать очередь, локальные поля, триггеры и production webhook.
