# Стратегия: LLM ведёт к тарифам 5 000 и 8 000 ₽

**Дата:** 2026-09-09  
**Статус:** канон для продукта / MAX / staff  
**Связано:** [playbook ясности](playbook-sales-clarity-funnel.md) · [тарифы 3/5/8](../history/2026-08-14-tariffs-stepwise-3000-5000-8000.md) · [ТЗ-26 bot_owned](../specs/26-max-llm-chat.md) · [ТЗ-33 kanban](../specs/33-staff-kanban-llm-stages.md) · `src/sfrfr/services/public_tariffs.py`

---

## 1. Цель

После диагностики клиент **сам** понимает, зачем следующий платный шаг, и принимает оферту на:

| Код | Публичное имя | Сумма | Когда предлагать |
|-----|---------------|-------|------------------|
| `DIAG` | Шаг 1. Диагностика | 3 000 ₽ | Комплект ИЛС + трудовая (bot_owned уже умеет) |
| `DOCS` (`ACCOMP` 5k) | Шаг 2. Подготовка документов | 5 000 ₽ | После **оплаченной** диагностики и выдачи понятного PDF/плана |
| `SUPPORT` (`ACCOMP` 8k) | Шаг 3. Сопровождение до подачи | 8 000 ₽ | После оплаты шага 2 **и** готовности проекта обращения / чек-листа подачи |

Можно остановиться после любого шага. LLM **не** продаёт «под ключ» и не склеивает 5+8 в один счёт без явного выбора клиента.

---

## 2. Принцип: правила двигают деньги, модель двигает ясность

```text
Детерминированные ворота (код)     LLM в MAX (текст)
─────────────────────────────      ─────────────────────────────
оплата DIAG                        объяснить «что сделали / что дальше»
эксперт опубликовал результат      пересказать план без сумм пенсии
клиент выбрал «готов к шагу 2»     озвучить 5 000 ₽ и состав DOCS
оферта + pay link                  напомнить ссылку / кабинет
оплата DOCS                        вести сбор недостающих документов
готов проект обращения             озвучить 8 000 ₽ и границу «подаёте сами»
```

LLM **не** создаёт счёт 5/8 «по настроению» и **не** двигает kanban в «Оплата» без факта оферты/заказа. Счёт и колонка — код + audit.

## 3. Воронка после шага 1 (диагностика)

### 3.1 Вход в зону 5 000 ₽

Обязательные ворота (все):

1. `DIAG` статус `paid`.
2. Результат диагностики **выдан клиенту** (PDF / secure link / сообщение «итог готов» по ТЗ-28/30) — не сырой OCR.
3. Клиент не в режиме `handed_to_operator` **или** сотрудник явно вернул боту ведение (`bot_resume`).
4. Нет открытого неоплаченного заказа DOCS/SUPPORT.

Тогда LLM (или правило + шаблон) говорит:

> По итогам диагностики понятен следующий объём: собрать комплект и черновики запросов.  
> Шаг 2 — подготовка документов, **5 000 ₽**. Можно остановиться здесь или идти дальше позже.  
> Решение о пенсии принимает только СФР; мы готовим документы и план — подаёте через СФР/Госуслуги вы сами.

CTA: принять условия в кабинете → pay link в MAX (как DIAG, флаг `MAX_BOT_OWNED_PAY_LINK` / staff «В MAX»).

### 3.2 Отказ / «подумаю» / «дорого»

Не торговать. Один шаг:

- вернуть к **одному** действию из плана диагностики (какой документ добрать);
- или кнопка «Позвать специалиста»;
- через N дней (ops) — мягкое напоминание без давления (marketing consent).

### 3.3 Когда 5 000 ₽ **не** предлагать

- Диагностика не оплачена / не выдана.
- Клиент явно выбрал «сам по чек-листу» — уважать, оставить путь к специалисту.
- Не хватает критичных исходников и эксперт пометил `needs_docs_before_docs_package`.
- Клиент просит сумму пенсии / гарантию — только позиция сервиса + специалист.

## 4. Воронка к 8 000 ₽

### 4.1 Вход

Обязательные ворота:

1. Заказ шага 2 (`DOCS` / ACCOMP 5000) `paid` **или** эксперт зафиксировал `docs_package_ready` после оплаты DOCS.
2. Есть артефакт «проект обращения / план подачи» (черновик в деле, не обязательно финальный PDF).
3. Клиент подтвердил интерес («хочу сопровождение» / кнопка / ответ на оффер).

Текст LLM:

> Шаг 3 — сопровождение до подачи, **8 000 ₽**: доводим проект обращения и пошаговый план.  
> Подачу через СФР / Госуслуги / МФЦ делаете вы; мы рядом с планом и ответами по шагам.  
> Можно остаться на шаге 2, если хотите подать сами по уже готовому комплекту.

### 4.2 Запреты

- Не обещать «подадим за вас», «гарантия перерасчёта», success fee.
- Не предлагать 8 000 ₽ вместо 5 000 ₽ «чтобы быстрее».
- Не смешивать LABOR_WORD (100 ₽/разворот) в тот же счёт без отдельного согласия.

## 5. Роль LLM в диалоге (промпт-канон)

Добавить в `CLIENT_CHAT_SYSTEM` / `docs/MAX/prompt-agent-client-chat.md` блок:

1. Цены только **3 000 / 5 000 / 8 000** (и 100 ₽/разворот трудовой) — без «от …», «10 000», «25 000».
2. Шаг 2 и 3 — только после соответствующих ворот; иначе возвращать к текущему шагу (ИЛС / диагностика / ожидание результата).
3. После PDF диагностики: сначала **понятность плана**, потом цена следующего шага (как ТЗ-27).
4. Soft-кнопки: `Готов к шагу 2 | Сам по плану | Нужен специалист` и позже `Сопровождение 8000 | Подам сам | Специалист`.
5. Оплата и оферта — ссылка на кабинет; pay URL не выдумывать.

Детерминированный код после кнопок «Готов к шагу 2/3»:

- проверить ворота;
- `create_order` с правильным `service_label` и суммой;
- сообщение с офертой;
- после `contract_accepted` — `issue_and_deliver_pay_link`.

## 6. Связь с kanban (staff)

Колонки продукта (см. ТЗ-33) должны отражать тарифные этапы, а не только «новый / в работе»:

| Этап клиента | Типичная колонка |
|--------------|------------------|
| До оплаты DIAG | Новый / Документы / Оплата DIAG |
| DIAG оплачен, ждём эксперта | Диагностика (staff) |
| Результат выдан | После диагностики |
| Оффер / оплата 5 000 | Оплата DOCS |
| DOCS в работе | Подготовка документов |
| Оффер / оплата 8 000 | Оплата SUPPORT |
| Сопровождение / подача клиентом | Сопровождение / Выдача |
| Закрыто / отказ | Закрыто / Отказ |

LLM **предлагает** следующий шаг клиенту; **колонку** меняет state machine по фактам (оплата, publish PDF, оферта), не «мнение модели».

---

## 7. Метрики успеха

- Конверсия DIAG paid → оффер DOCS (7 дней).
- Конверсия оффер DOCS → paid.
- Конверсия DOCS paid → оффер SUPPORT → paid.
- Доля отказов с причиной «цена» / «сам» (без давления в чате).
- Жалобы на обещание перерасчёта = 0 (контент-гард).

---

## 8. Что не делать в v1

- Автодиагноз и авто-PDF без HITL.
- Автосчёт 5/8 без оплаты DIAG и без выдачи результата.
- Один «пакет 13 000» вместо поэтапных шагов.
- Перенос карточки kanban «по тексту клиента» без проверки ворот.
