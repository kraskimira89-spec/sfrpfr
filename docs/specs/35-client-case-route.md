# ТЗ: «Мой маршрут» в клиентском кабинете (срез «Собираем документы»)

**Дата:** 2026-10-25  
**Статус:** направление принято (спокойный маршрут без баллов) · первый UI-срез  
**Канон кабинета:** [03-client-cabinet.md](03-client-cabinet.md) · карта работы: `client_work_map.py` / `CaseWorkMap`  
**Не делать:** баллы, рейтинги, серии, награды за оплату, % «до пенсии», новый платёжный поток, Tracker при открытии страницы

## 1. Принцип

Клиентские **главы** — представление уже существующих ступеней `work.stages` / `status_key`.  
Не вводить второй backend-статус и не дублировать admin-воронку из 13 ступеней как клиентский процесс.

## 2. Сопоставление ступеней → главы

| Глава (клиент) | `stages.n` сейчас | Когда `current` (по `status_key` / флагам) | Admin funnel (ориентир, не SoT UI) |
|---|---|---|---|
| Знакомство | 1 | `consent` | contact |
| Документы | 2 | `waiting_docs`, `need_info` | documents |
| Проверка | 3 | `docs_review`, `diagnosis` | diagnostics |
| План действий | 4 | `result_ready` (есть PDF/итог) | plan / result prep |
| Итоги | 5 | `done` | result / feedback |

Внутренние 13 admin-ступеней остаются в staff UI; клиенту не показываются.

## 3. Таблица «элемент экрана → источник данных»

| Элемент экрана | Источник | Есть сейчас? |
|---|---|---|
| Полоса глав + «Вы здесь» | `work.stages[]` (`state`: done/current/todo) | да |
| Заголовок текущей главы | маппинг в `case-route.ts` от `stages` / `status_key` | адаптер |
| «Ваш следующий шаг» (что/зачем) | `work.now_need`, `work.cta_*`, `SLOT_PURPOSES` / doc slot | да |
| Кнопка загрузки | существующий `onUpload` + слот `documents[]` | да |
| «Где получить?» | `work.ils_howto_url` (для ИЛС); иначе чат | частично |
| «Нужна помощь» / «Не могу получить» | якорь `#case-chat-input` (тот же чат) | да (ссылка) |
| Комплект документов | `work.documents[]` (`status`, `status_label`, `need`) | да |
| «N из M обязательных» | `required_uploaded` / `required_total` | да |
| «Сейчас работает специалист» | `cta_key === wait` и пустые `next_actions` | да |
| Специалист (имя) | — | **нет API** (есть только `expert_assigned: bool`) |
| Последние события (лента) | производные от `documents[].added_at` + статусы слотов | **упрощённо**; полной client-audit ленты нет |
| Контрольная дата | `next_action_at` | **не отдаётся** в client `work` |
| Предупреждение СФР | `detail.warning` / константа ТЗ | да |

## 4. Чего пока нет в API (gaps)

1. Имя/отображаемое ФИО ответственного сотрудника для клиента.  
2. Публичная лента значимых событий (без служебных audit/OCR).  
3. `next_action_at` / контрольная дата в payload `work`.  
4. Отдельный флаг «документ невозможно получить» (пока только чат).  
5. Allowlist-тексты причин reupload из заметки чек-листа (частично есть generic «нечитаемый файл»).

Первый срез **не** добавляет эти поля в API, кроме явного честного UI: «Специалист ещё не назначен» / «События появятся по мере работы».

## 5. Границы реализации среза

- Только клиентский кабинет (`apps/cabinet`).  
- Без изменения фактов оплаты/подачи.  
- Без клиентских напоминаний и Tracker.  
- Без auto-merge PR на прод до ручной приёмки экрана.
