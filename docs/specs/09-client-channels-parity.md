# ТЗ-09: паритет мини-приложения MAX и веб-кабинета клиента

> **Актуальное продуктово-техническое решение 2026-09-01:** личного кабинета
> клиента в MAX нет и не будет. Чат MAX и плавающий чат веб-кабинета — один
> диалог по `case_id`: общая история, ответы бота и специалиста. Документы,
> согласие и оплата — только на сайте, в разделе «Мои документы» кабинета.
> `/app/` — заглушка, не клиентский кабинет.

## Цель

Исторически планировался паритет двух UI. **Актуальный канон:**

1. **личный чат MAX и чат веб-кабинета** — одна текстовая переписка;
2. **веб-кабинет** (`cabinet.домен`) — **единственный** клиентский кабинет и место загрузки документов;
3. **мини-приложение** (`/app/`) — **закрыто как ЛК** (legacy URL / заглушка).

Источник истины — FastAPI + Supabase. WordPress только приводит к контакту; ПДн и файлы туда не попадают.

## Для кого ТЗ

Кодер (Agent mode): API, `apps/cabinet`, `web/max-miniapp`, лендинг/бот, миграции.

## Текущее состояние (исходная точка)

| Канал | Стек | Что умеет сейчас | API |
|---|---|---|---|
| `/app/` bridge | `web/max-miniapp` | объяснить границы MAX и открыть бот/веб-кабинет | статический bridge, не клиентский ЛК |
| Веб-кабинет | `apps/cabinet` | OTP, список дел, карточка, согласия, оплаты, результат, сообщения | `/api/portal/*` (JWT) |

Цель: два интерфейса одного API-источника сообщений. Связка MAX ↔ аккаунт кабинета выполняется через `clients.max_user_id` и общий `case_id`.

## Принципы

1. **Один `case_id` — два UI.** Смена канала не создаёт второе дело.
2. **Один контракт данных.** Чат MAX и веб-чат читают/пишут общую историю через согласованный client API.
3. **Паритет переписки**, не паритет всех функций. Документы, согласия, оплата и операции по делу выполняются в веб-кабинете.
4. **Переключение интерфейса — продуктовый выбор**, а не создание второго канала.
5. **Без кнопки «подать в СФР за клиента»** в обоих UI.
6. **Предупреждение** на ключевых экранах: «Решение принимает СФР. Результат не гарантирован».

## 1. Выбор канала клиентом

### 1.1. Точки выбора

| Место | Поведение |
|---|---|
| WordPress CTA «Начать проверку» | Ведёт к началу диалога; клиент может продолжить его в MAX или веб-кабинете |
| Бот MAX (первый контакт / `/start`) | CTA «Кабинет на сайте» → веб-URL; **не** mini-app |
| `/app/` bridge | Ссылки на чат MAX и веб-кабинет; не выдавать его за ЛК |
| Веб-кабинет (шапка/меню) | Блок «Открыть этот чат в MAX» → ссылка на того же бота |
| Email/SMS уведомления | Нейтральное сообщение без ПДн и содержимого чата; при необходимости — ссылка на кабинет |

### 1.2. Предпочтение канала

Хранить у клиента (или у связи client↔case):

```text
preferred_channel: max_miniapp | web_cabinet | unset
preferred_channel_set_at: timestamptz
```

- При первом явном выборе — сохранить.
- Клиент может сменить в настройках кабинета; `/app/` не является интерфейсом дела.
- Не блокировать другой канал: предпочтение влияет на CTA и уведомления по умолчанию, не на доступ.

### 1.3. Копирайт выбора (коротко)

- «В MAX — удобно с телефона»
- «В кабинете — удобно с компьютера и большим экраном»
- Оба варианта: один чат, одна история, одно дело

## 3. Модель идентичности и связка каналов

### 3.1. Сущности

```text
clients
  id
  full_name
  phone / email
  preferred_channel
  max_user_id          -- nullable, unique
  auth user_id         -- Supabase auth.users, nullable до первого OTP

cases
  id
  client_id
  ...существующие поля...
```

### 3.2. Сценарии линка

**A. Сначала MAX**

1. Клиент пишет боту MAX → создаётся/находится дело по `max_user_id`.
2. В боте: «Открыть кабинет на сайте» → OTP на телефон/email.
3. После OTP: `clients.max_user_id` и `clients.user_id` связаны.
4. Веб-кабинет показывает то же дело.

**B. Сначала веб**

1. OTP → кабинет → дело.
2. «Открыть этот чат в MAX» → бот `/start` или обычная ссылка на диалог.
3. При первом сообщении — привязка `max_user_id` к `client_id` (с подтверждением OTP, если уже есть другой max_user).

**C. Конфликт**

- Один `max_user_id` не может принадлежать двум clients.
- При конфликте — сообщение оператору + клиенту «уже привязано»; без автослияния ПДн.

### 3.3. API связки (минимум)

```text
POST /api/portal/auth/otp/request
POST /api/portal/auth/otp/verify
POST /api/portal/link/max          -- JWT + max_user_id / initData
POST /api/portal/link/web-from-max -- из mini-app: старт OTP
GET  /api/portal/me                -- профиль + preferred_channel + linked flags
PATCH /api/portal/me/preferences   -- preferred_channel
```

Проверка подписи MAX WebApp `initData` — на сервере (не доверять голому `user_id` из query в проде).

## 4. Единый client API (целевой контракт)

Старый mini-app-контур не расширяется. Чат MAX и веб-кабинет используют единый контур сообщений.

### 4.1. Обязательные методы для обоих UI

```text
GET  /api/portal/me/cases
GET  /api/portal/cases/{id}
POST /api/portal/cases                    -- создать дело (если нет)
POST /api/portal/cases/{id}/documents
GET  /api/portal/cases/{id}/documents
POST /api/portal/cases/{id}/run           -- или /request-review (единая семантика)
GET  /api/portal/cases/{id}/findings
GET  /api/portal/cases/{id}/draft
GET  /api/portal/cases/{id}/checklist
GET|POST messages, consents, orders, result  -- как в текущем portal
```

Для сообщений обязательны: `id`, `case_id`, `author_kind`, `channel_origin`,
`created_at`, `updated_at`, `delivered_at`, `read_at_client`, `read_at_staff`.
`external_message_id` уникален для идемпотентной обработки webhook MAX.

Авторизация:

- веб: `Authorization: Bearer <JWT>`;
- MAX webhook: доверенный серверный контекст `max_user_id`; веб-кабинет: `Authorization: Bearer <JWT>`.

### 4.2. Deprecation

- `/api/cases/open` и старый mini-app — legacy bridge; новые функции туда не добавлять.

## 5. Задачи по фронтам

### 5.1. `apps/cabinet` (веб)

В веб-кабинете сохранить функции дела и довести общий чат до единого канона:

- кнопка **«Запустить проверку»** (или эквивалент `run` / request-review);
- блок findings;
- единый плавающий чат по `case_id` с общей историей MAX ↔ кабинет;
- одну кнопку **«Открыть этот чат в MAX»** в карточке вопросов по делу;
- в списке действий — текстовую ссылку **«Написать в чате кабинета»** на `#case-chat-input`;
- deep-link `cabinet.домен/cases/{id}` из писем и из mini-app.

Сохранить: OTP, согласия, оплаты, результат, сообщения. Вложения из чата
не принимать; документы загружаются только через «Мои документы».

### 5.2. `web/max-miniapp`

Оставить только статический bridge без авторизованного доступа к делу:

- объяснение, что клиентского кабинета в MAX нет;
- ссылка **«Открыть чат в MAX»**;
- ссылка **«Открыть веб-кабинет»** для документов, согласий, оплаты и операций по делу.

Не добавлять в `/app/` список дел, загрузку документов, оплату или отдельную
историю сообщений.

### 5.3. Бот MAX и единый чат

- `/start`: открыть диалог и при необходимости дать ссылку на веб-кабинет;
- текстовые сообщения MAX сохранять в общей истории `case_messages` по `case_id`;
- команда/кнопка «Веб-кабинет» ведёт к сайту, где находятся документы, согласия и оплата;
- вложения в чат не сохранять, а отвечать CTA «Мои документы»;
- уведомления о новых сообщениях не дублировать при активном чате клиента.

### 5.4. WordPress

- CTA ведёт на страницу/якорь выбора канала (не только в MAX).
- По-прежнему без upload СНИЛС/сканов на WP.

## 6. UX-ограничения

- Первый экран после входа: статус + следующее действие + CTA загрузки/проверки (без перегруза).
- На мобильном веб-кабинете чат открывается как full-screen panel или bottom sheet.
- В шапке и empty state явно указано: это один чат в кабинете и MAX.
- Не дублировать MAX CTA на одном экране: одна кнопка в карточке вопросов по делу.
- Одинаковые тексты предупреждений и статусов.
- Ошибки API показывать человекочитаемо в обоих UI.

---

## 7. Безопасность и ПДн

- RLS: клиент видит только свои `case_id`.
- Signed URL с TTL только для файлов, загруженных через веб-кабинет.
- Audit log: upload, consent, link max↔web, смена preferred_channel, run.
- Не передавать в MAX и аналитику storage URL, СНИЛС, паспортные/банковские данные,
  OCR-текст и ПДн из документов.
- CORS: `cabinet.домен`; `/app/` — статический bridge без доступа к данным дела.
- Запрет прямой выдачи service role в браузер.

## 8. Этапы реализации для кодера

### Этап A — связка и предпочтение (фундамент) ✅ реализовано

1. Миграция: `max_user_id`, `preferred_channel` у clients.
2. `GET/PATCH /api/portal/me` (+ preferences).
3. Link MAX↔web (OTP + initData verify).
4. CTA выбора на WP и в боте.

### Этап B — единый чат и паритет операций по делу ✅ реализовано

1. Portal: `run` / findings / draft / checklist единым контрактом.
2. Веб-кабинет: кнопки проверки, findings и плавающий чат по `case_id`.
3. MAX: общий текстовый чат, ссылка на веб-кабинет для документов; `/app/` оставлен bridge.

### Этап C — доведение Should ✅ реализовано

1. Оплаты ЮKassa — только в веб-кабинете (`POST .../orders/{id}/pay`, webhook, опциональный чек).
2. Результат и сообщения доступны в кабинете и общей переписке MAX.
3. `/app/` не расширяется: deep-link ведёт в веб-кабинет или чат MAX.

### Этап D — приёмка и регресс (частично ✅)

1. Unit/авто: конфликт `max_user_id` 409, CTA по `preferred_channel`, `/cases/{id}`, representatives API.
2. Чеклист QA: [docs/qa/tz09-stage-d.md](../qa/tz09-stage-d.md) — пошаговый runbook; ручные E2E 1–5 ещё открыты (нужен тестовый MAX). Smoke API/витрина на `taxi-doroga-dobra.ru` — OK; `proverkastaza.ru` ждёт DNS.
3. Уведомления о новых сообщениях и смене статуса: нейтральный текст без ПДн,
   без дубля при активном чате; системное сообщение хранится в общей истории.

## 9. Критерии приёмки

1. Клиент может вести **одно** дело и открыть один чат по нему в MAX и `cabinet.домен`.
2. Сообщение из MAX появляется в кабинете, а сообщение из кабинета — в MAX;
   история упорядочена по серверному времени.
3. Повторный webhook MAX не создаёт дубликат благодаря уникальному `external_message_id`.
4. Статусы и findings совпадают в кабинете и MAX, где они доступны.
5. Вложения в чате не сохраняются; документы загружаются только через «Мои документы».
6. Нет возможности подать заявление в СФР от имени клиента ни в одном UI.
7. Чужой `case_id` недоступен (403/404) в обоих интерфейсах.
8. На странице нет двух одинаковых MAX CTA: одна кнопка — в карточке вопросов по делу.
9. Уведомления не содержат ПДн и не дублируются при активном чате.
10. Автотесты: общий чат, идемпотентность webhook, upload ACL, unread/read и notification suppression.

## 10. Тест-план (минимум)

- [ ] MAX → дело → сообщение → то же сообщение видно в веб-кабинете
- [ ] Веб-кабинет → сообщение → то же сообщение доставлено в MAX
- [ ] Повторная доставка webhook не создаёт вторую запись
- [ ] Вложение в MAX отклоняется и ведёт в «Мои документы»
- [ ] Веб-чат блокирует file upload/drag/paste
- [ ] Активность в одном интерфейсе подавляет дублирующее уведомление
- [ ] На desktop/tablet/mobile открывается один чат по делу
- [x] Конфликт: второй auth не перехватывает чужой `max_user_id` (unit)
- [x] Preferred channel меняет порядок ссылок в уведомлении (unit + рассылка при смене статуса)
