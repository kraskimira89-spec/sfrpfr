# Контракты переходов при ошибке и претензии

Канон условий «можно сказать / сделать». Индекс: [`client-ai-error-docs-index.md`](client-ai-error-docs-index.md).  
Тексты: [`client-ai-error-response-catalog.md`](client-ai-error-response-catalog.md).  
Доказательства: [`client-ai-evidence-requirements.md`](client-ai-evidence-requirements.md).

Логические имена ниже — контракт спецификации. Наличие одноимённых Python-модулей **не** означает, что live-handler уже их исполняет (см. gaps).

## 1. Сказано ≠ выполнено ≠ подтверждено

| Утверждение | Требуемое событие |
|---|---|
| «Сохранено» | Успешная запись |
| «Обращение зарегистрировано» | Успешная регистрация и предусмотренный идентификатор |
| «Зарегистрировать не удалось» | Подтверждённый сбой или отказ; указаны доступный следующий шаг и сохранённые сведения |
| «Передано специалисту» | Назначение подтверждено (отдельно от создания задачи) |
| «Проверка идёт» | Фактический запуск (queued ≠ running) |
| «Результат доступен» | Проверенный доступ к версии |
| «Исправлено» | Persist + проверка |
| «Уведомление отправлено» | Факт отправки |
| «Клиент ознакомился» | Не выводить из факта отправки |
| «Принято клиентом» | Не выводить из прочтения / молчания |

Отказ или сбой регистрации **не** основание сказать «зарегистрировано».  
Если процесс **не** предусматривает номера — это описывается явно в ответе; модель **не** придумывает идентификатор.

Неизвестный исход внешней операции → сверка, не слепой повтор.

## 2. Приём сообщения и претензии

```text
Сообщение получено
→ сохранено в разрешённом контуре
→ выделены требования
→ регистрация по установленному процессу
→ сбор и проверка доказательств
```

- Полная проверка доказательств **не** обязательна для принятия претензии.
- Проверка доступа ограничивает раскрытие и действия, **не** стирает обращение.
- Регистрация претензии **не** авто: стоп всего заказа, отмена оплаты, удаление документов, признание расчёта, закрытие пенсионного вопроса.

## 3. Временное ограничение до вывода

```text
Признак существенной ошибки
→ отметка «требует проверки»
→ ограничение зависимого действия по политике
→ проверка
→ подтверждение ошибки либо восстановление актуальности
```

Временная отметка **не** есть признание ошибки. Применять адресно; фиксировать основание.

## 4. Две независимые плоскости исправления

| Плоскость | Готовность |
|---|---|
| Причина | Устранён шаблон / данные / расчёт / переход / иной компонент + проверка |
| Последствия | Затронутые материалы и действия проверены и обновлены |

Исправление шаблона **не** обновляет автоматически ранее выданные отчёты.  
Исправление одного отчёта **не** доказывает устранение системной причины.

## 5. Уведомление — отдельный переход

```text
Исправление подготовлено
→ проверено
→ сохранено
→ доступно авторизованному клиенту
→ уведомление отправлено
→ статус доставки в доступном объёме
```

Отправлено ≠ прочитано ≠ принято.

## 6. Контуры закрытия (не одним действием)

| Контур | Правило |
|---|---|
| Технический дефект | Завершение — причина устранена и проверена |
| Результаты дела | Зависимости проверены; актуальные версии доступны |
| Требование клиента | Решение принято и исполнено по своему процессу |
| Коммуникация | Корректный итог передан или зафиксирована невозможность доставки |
| Пенсионный вопрос | Завершение — по подтверждённому результату и согласованным критериям |
| Сопровождение при открытом вопросе | Может завершиться отдельно; сохраняются нерешённые вопросы, причины и дальнейший маршрут |

Оставить пенсионный вопрос открытым — допустимый итог **сопровождения**, но **не** завершение самого пенсионного вопроса.

«Спасибо» клиента ≠ доказательство исполнения.

## 7. Сквозной конвейер ошибки

```text
Сообщение о возможной ошибке
→ сохранить сообщение и требования
→ зарегистрировать нужные обращения
→ оценить риск использования спорного результата
→ при необходимости — адресное ограничение
→ собрать и проверить доказательства
→ вывод по каждому пункту
→ решение уполномоченного
→ параллельно: устранение причины ‖ исправление последствий в деле
→ предоставить безопасный актуальный результат клиенту (когда готов)
→ уведомить клиента
→ раздельно проверить критерии завершения (в т.ч. tech-дефект)
```

После подтверждения ошибки работа идёт в **двух связанных направлениях**: устранение причины и исправление последствий.  
Безопасное исправление конкретного дела и уведомление клиента **не обязаны** ждать полного устранения системной причины.  
Технический дефект при этом остаётся открытым до собственной проверки.  
Действия, зависящие от ещё не устранённой причины, остаются ограниченными.

Недостаточно сведений → «требуется уточнение», **не** автоматически «ошибки нет».

## 8. Составные требования

Одна реплика может нести несколько независимых элементов (обвинение, отказ от оплаты, возврат, исправление расчёта).  
Каждый получает свой статус. Запрещён единственный ответ «передали жалобу».

## 9. Частичные сбои и повторы

| Ситуация | Правило |
|---|---|
| Повтор той же команды | Идемпотентность по идентификатору операции; без второй претензии |
| Неполное сохранение | Операция не «завершена»; клиенту не говорить «исправлено» / «принято» |
| Неизвестный исход | Сверка |
| Сбой хранения доказательства | Не создавать фиктивную ссылку |
| Сообщение об успехе | Только после проверки результата операции |

## 10. Аварийное ограничение

Если нужно немедленно прекратить распространение заведомо недостоверного утверждения — по утверждённому аварийному порядку, **не** дожидаясь полного разбора для продолжения ложного статуса.
