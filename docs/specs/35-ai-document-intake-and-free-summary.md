## 1. Контекст и проблема

В репозитории уже есть:

- кабинет (`apps/cabinet`) и админка (`apps/admin`, карточка `/c/[caseId]`);
- ingest worker + OCR v2 (text layer → Yandex Vision → Tesseract);
- HITL-панель `IngestReviewPanel` и API ingest-review;
- AI orchestrator (`src/sfrfr/ai/orchestrator.py`);
- тарифы DIAG 3k / DOCS 5k / SUPPORT 8k и kanban ТЗ-33.

Разрывы, которые закрывает это ТЗ:

1. Клиент загружает файлы и **не** получает понятную цепочку статусов до бесплатного резюме.
2. Специалист **не всегда** видит дело + оригинал + OCR + confidence в одном месте и не всегда попадает в очередь проверки (особенно трудовые).
3. ИИ-анализ может уходить вперёд без подтверждения сомнительного OCR.
4. Нет обязательного **бесплатного** краткого резюме *до* продажи подробного анализа за 3 000 ₽.
5. amoCRM в контур **не** входит (выключена).

## 2. Цель

Управляемый конвейер:

```text
заявка → загрузка → приём файла → OCR →
  (трудовая / низкая уверенность → HITL специалиста) →
подтверждённые данные → ИИ-анализ расхождений →
бесплатное резюме клиенту → оффер DIAG 3 000 →
(после оплаты и выдачи) DOCS 5 000 → SUPPORT 8 000
```

## 3. Границы

### Входит

- статусы документа/дела для клиента и staff (надстройка над существующими, без ломки enum без миграции);
- карточка файла: статус, тип, confidence, HITL-флаг;
- очередь OCR (существующий worker);
- хранение OCR + audit правок;
- admin: дело, файлы, split-view оригинал|OCR, accept/edit/reupload;
- блок анализа только после подтверждения;
- генерация и показ бесплатного резюме;
- предложение тарифов 3/5/8 по правилам;
- журнал аудита.

### Не входит

- amoCRM (поля, sync, вебхуки, UI);
- автоподача в СФР/Госуслуги;
- обещание перерасчёта / суммы;
- GPT-vision как OCR (канон ТЗ-13);
- новая Celery/Redis-очередь;
- массовая миграция архивных дел.

## 4. Роли

Как в `PROJECT_CONTEXT.md`. Кратко:

- **Клиент** — статусы файлов/дела, резюме, оффер; без сырого OCR и внутренних confidence.
- **Специалист** — очередь HITL, правка, подтверждение, gate на анализ и публикацию резюме.
- **ИИ/OCR** — текст, тип, поля, confidence, черновик расхождений и резюме по шаблону; без юридического утверждения.

## 5. Типы документов (минимум)

ИЛС / сведения о стаже; трудовая; справки о стаже/заработке; ответы СФР; паспорт (условно); прочее — по ТЗ-32 сценариям.

Поля карточки файла — как в ТЗ-13 + `ingest_status`, `ingest_review_required`, `ocr confidence`, версии OCR/HITL.

## 6. Статусы документа (целевые лейблы)

Маппить на существующие `uploaded / under_review / accepted / needs_reupload / …`, не дублировать без нужды:

```text
uploaded → validation_failed | queued_for_ocr → ocr_processing →
ocr_completed → manual_review_required | verified |
reupload_requested | rejected → analysis_ready
```

## 7. Правило ручной проверки

HITL **обязателен**, если хотя бы одно:

- confidence ниже порога (канон `INGEST_*` из ТЗ-13);
- рукопись, помарки, обрез, низкое качество фото;
- тип не определён;
- конфликты между страницами;
- **документ — трудовая книжка (всегда)**;
- критичные разрывы периодов на уровне quality gate.

Пока `ingest_review_required=true` — **не** запускать classify/extract/analyze автоматически (кроме явного «продолжить» экспертом, с аудитом).

## 8. Экран специалиста

Расширить существующие `case-funnel-main` + `IngestReviewPanel`, не строить второй UI:

- статус дела, следующий шаг, счётчики HITL / reupload / готовность к анализу / резюме;
- список документов с типом, статусом, confidence, меткой HITL;
- split-view: оригинал (signed URL) | текст | поля | причины HITL;
- действия: подтвердить / сохранить правки / reupload / отклонить;
- audit: OCR-значение, правка, автор, время.

## 9. ИИ-анализ расхождений

Условия старта:

- обязательные документы `verified` / `accepted` (или явно исключены);
- нет открытых reupload;
- gate специалиста **или** авто-правило только для non-labor + высокая уверенность (продуктово зафиксировать в коде флагом).

Черновик структуры: учтённые документы; подтверждённые сведения; периоды внимания; возможные расхождения; пробелы; следующий шаг; confidence по выводам.  
Явно разделять: факт / предположение / пробел / вопрос специалисту.

Запрет: гарантированный перерасчёт и суммы.

## 10. Бесплатное резюме клиенту

После анализа (и при необходимости approve специалиста):

1. Статус документов (принято / нужен повтор / не хватает).
2. Итог: «есть сведения к дополнительной проверке» | «явных расхождений не видно (предварительно)» | «мало данных».
3. Следующий шаг: подробный анализ **3 000 ₽** (DIAG); при запросе обращений — 5 000; при делегировании контроля — 8 000.
4. Disclaimer позиции о подаче и отсутствии гарантии.

Пример (шаблон):

> Мы приняли и предварительно проверили ваши документы.  
> В сведениях есть данные, которые рекомендуется проверить подробнее (периоды/записи из разных источников).  
> Это предварительный результат, не гарантия перерасчёта.  
> Следующий шаг: подробный анализ — 3 000 ₽.

## 11. Коммерческая логика

| Уровень | Цена | Код | Содержание |
|---------|-----:|-----|------------|
| Бесплатное резюме | 0 | — | короткий статус + осторожный вывод |
| Подробный анализ | 3 000 | `DIAG` | детальный разбор, план, PDF по канону 27–30 |
| Анализ + обращения | 5 000 | `DOCS` | + проекты обращений, приложения, инструкция |
| Сопровождение | 8 000 | `SUPPORT` | + сроки, ответы, ведение; **подаёт клиент** |

Правила оффера: неполные документы → сначала запрос файлов; есть возможные расхождения → по умолчанию DIAG; клиент просит заявления → DOCS; хочет контроль до результата → SUPPORT.  
Счета и kanban — детерминированно (ТЗ-33), LLM только ясность (ТЗ-26).

## 12. Уведомления

События: загружено; в обработке; нужен повторный скан; на проверке специалиста; резюме готово; нужны доп. документы; выбран тариф; ждём оплату; работа начата; новый результат.  
Без ПДн, паспорта, СНИЛС, сырого OCR, категоричных обещаний.

## 13. Безопасность

- доступ к файлам только владелец дела / staff; signed URL с TTL;
- redaction в LLM (`redact_for_llm`);
- audit OCR, HITL, запусков анализа, публикации резюме;
- внешний ИИ — только утверждённый контур (Yandex Vision / LLM проекта);
- стоп-кран специалиста на авто-пайплайн.

## 14. Критерии готовности первой версии

На обезличенном деле:

1. Создать заявку и загрузить тестовую трудовую (PDF/фото).
2. Клиент видит «принято / проверяется».
3. Admin: дело + файлы видны.
4. OCR + low-confidence / трудовая → HITL.
5. Специалист правит поле и подтверждает.
6. Analyze стартует только после подтверждения.
7. Черновик резюме → показ клиенту без гарантий.
8. Оффер DIAG 3 000 виден.
9. Нет ПДн/секретов в Git/логах; amoCRM не задействована.

### Почему «загрузил — тишина» и «специалист не видит»

1. Worker ingest не крутится / job в `security_check` — клиент висит на прогрессе.
2. Статус **дела** (`pipeline_status`) и статус **файла** (`ingest_status`) разделены; после upload дело часто остаётся `intake`.
3. В кабинете после `under_review` нет шагов «OCR готов / HITL / резюме готово».
4. `IngestReviewPanel` скрыт, если очередь HITL пуста; OPERATOR не видит OCR; эксперт — только назначенные дела.
5. Artifacts/оригинал недоступны, пока quarantine / `OcrSourceUnresolved`.
6. **Трудовая не всегда HITL:** в `document_ingest_v2` флаг `ingest_review_required` ставится по качеству OCR, а не по типу `labor_book`. В `document_ingest.py` `is_labor` даёт только `labor_timeline_drafts`, без принудительного review.
7. Оферта DIAG часто идёт после «ИЛС+трудовая есть», **минуя** бесплатное резюме по распознанным данным.
8. **Конфликт документов:** [`b2c-customer-journey.md`](../b2c-customer-journey.md) и часть playbook’ов всё ещё описывают путь через `diagnostic_paid` **до/вокруг** разбора сканов; целевой канон — этот файл + `PROJECT_CONTEXT` (docs → OCR → HITL → **free summary** → DIAG). При реализации этапа E/F обновить `b2c-customer-journey.md` и ссылки в маркетинге, не плодить третью модель.
