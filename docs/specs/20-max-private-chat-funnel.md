# ТЗ-20: воронка клиента через личный чат MAX

**Статус:** в реализации (сайт CTA + FSM бота)  
**Дата:** 2026-08-04  
**Для кого:** backend / frontend / WordPress-разработчик / QA  
**Связанные ТЗ:** [ТЗ-09](09-client-channels-parity.md), [ТЗ-03](03-client-cabinet.md), [ТЗ-12](12-amocrm.md), [ТЗ-13](13-document-ingest-v2.md)

## 1. Цель и границы

Сделать личный чат MAX понятной точкой входа в услугу с сайта. Бот проводит клиента через короткую диагностику, а MAX и веб-кабинет продолжают **один чат по делу** с общей историей. Согласие и загрузка документов остаются в **личном кабинете на сайте**.

В scope:

- CTA сайта → личный чат MAX;
- стартовый сценарий и меню бота;
- хранение результата диагностики;
- переход в **веб-кабинет** с сохранением одного `case_id`;
- передача контекста оператору и в amoCRM;
- аналитика и E2E-приёмка.

Out of scope:

- автоматическая подача в СФР;
- LLM-консультация в первом диалоге;
- изменение финансовой воронки, правил оплаты и OCR-пайплайна.

## 2. Решения, обязательные для реализации

1. Все новые главные CTA сайта с текстом «Начать проверку», «Написать в MAX», «Получить помощь» ведут на `MAX_CHAT_URL` — личный чат бота.
2. Канал MAX и прямой URL mini-app не являются CTA первого уровня на сайте. Они допустимы в футере, справке и после старта диалога.
3. Бот не создаёт дело автоматически на `/start`. Дело создаётся после выбора цели и подтверждения перехода в кабинет либо при запросе оператора.
4. **Документы:** только раздел «Мои документы» в личном кабинете на сайте (защищённо, после согласия). Если клиент прислал файл **в чат**, не сохранять его и ответить с CTA в раздел документов.
5. Решающий первый сценарий — детерминированное дерево кнопок. Не подключать LLM до отдельного ТЗ, чтобы исключить непредсказуемые ответы и обработку лишних ПДн.  
   Свободный текст без LLM: короткий ответ «ответьте кнопками / позовите специалиста» + клавиатура текущего шага (`free_text_nudge`).  
   Будущий LLM-контур — только по [ТЗ-26](26-max-llm-chat.md) и явному go.
6. Клиент всегда видит кнопку «Позвать специалиста». Эта ветка не требует ответа на все вопросы.
7. **Личного кабинета клиента в MAX нет и не будет.** Клиентский кабинет — только сайт (`CABINET_PUBLIC_URL`). Mini-app `/app/` — не ЛК (заглушка). Чат MAX и плавающий чат кабинета используют одну историю по `case_id`.

| Сущность | Назначение | URL / настройка |
|---|---|---|
| Личный чат MAX | Первый контакт, диагностика, поддержка | `MAX_CHAT_URL`, сейчас `https://max.ru/id8905998693_1_bot` |

## 4. Клиентский сценарий бота

### 4.1 Первый экран

Текст:

> Здравствуйте! Поможем разобраться со стажем и документами для СФР. Решение о пенсии и перерасчёте принимает СФР. С чего начнём?

Кнопки:

1. `Проверить стаж` → `intake:goal:check_experience`
2. `Не хватает периода работы` → `intake:goal:missing_period`
3. `Есть отказ или вопрос СФР` → `intake:goal:sfr_question`
4. `Спросить специалиста` → `intake:goal:operator`

Команды-синонимы: `/start`, `Начать`, `Старт` открывают этот экран. Повторный `/start` не стирает уже сохранённую диагностику без явной кнопки «Начать заново».

### 4.2 Диагностика

После первых трёх целей задать максимум три вопроса, показывая один вопрос за раз:

| Поле | Вопрос | Кнопки |
|---|---|---|
| `ils_available` | «Есть выписка из индивидуального лицевого счёта (ИЛС)?» | «Да», «Нет», «Нужно получить», «Не знаю, как получить» |
| `employment_records_available` | «Есть трудовая книжка или справки о работе?» | «Да», «Часть документов», «Нет» |
| `device_preference` | «Как вам удобнее открыть кабинет на сайте?» | «С телефона», «С компьютера», «Нужна помощь» (`intake:device:max|web|help`) |

Если по ИЛС ответ не «Да» — промежуточный экран инструкции: шаги на Госуслугах, ссылки на портал и статью блога, вариант МФЦ/СФР, кнопка «Уже получил(а) — дальше», специалист. Только после подтверждения — дальше к устройству/кабинету. В legacy-ветке при «Нет» по трудовой — краткая инструкция + «Продолжить без полного комплекта».

Правила:

- не спрашивать СНИЛС, паспортные данные, даты рождения, места работы, номера дел и другие ПДн в чате;
- кнопка «Назад» доступна на втором и третьем вопросе;
- «Нужна помощь» в любом вопросе создаёт запрос оператору и не блокирует клиента;
- `sfr_question` после первого вопроса может сразу предложить кабинет и оператора: дополнительные вопросы необязательны.

### 4.3 Резюме и переход

После диагностики показать короткое резюме по шаблону:

> Поняли. Для начала нужно передать доступные документы и сверить их с данными ИЛС. Загрузите файлы через раздел «Мои документы» в кабинете на сайте. Вопросы можно писать в MAX или в кабинете — это один чат по делу. Перед загрузкой потребуется согласие на обработку данных.

Главная кнопка (одна):

- `Кабинет на сайте` → URL веб-кабинета (`CABINET_PUBLIC_URL`, с `case_id` при наличии);
- при `device_preference=help` сверху дополнительно `Позвать специалиста`.

Вторичные кнопки: `Какие документы пригодятся`, `Позвать специалиста`, `Начать заново`.  
**Не** показывать «В MAX — кабинет» / mini-app как кабинет.

### 4.4 Меню для вернувшегося клиента

Настроить меню команд бота и дублировать его кнопками:

| Команда | Назначение |
|---|---|
| `/start` | начать или продолжить диагностику |
| `/cabinet` | открыть личный кабинет для текущего дела |
| `/status` | получить статус текущего дела |
| `/documents` | показать список нужных документов и CTA кабинета |
| `/help` | помощь и оператор |

Если в MAX Bot API поддерживается `PATCH /me/commands`, зарегистрировать команды при деплое/инициализации. Иначе сохранить функциональные текстовые команды и добавить задачу в README разработчика.

## 5. Данные и интеграции

### 5.1 Новая/расширенная модель intake

Добавить к существующему клиенту или кейсу отдельную запись `max_intake` (предпочтительно отдельной таблицей с audit-полями):

```text
id: uuid
client_id: uuid | null
case_id: uuid | null
max_user_id: text
goal: check_experience | missing_period | sfr_question | operator
ils_available: yes | no | unknown | null
employment_records_available: yes | partial | no | null
device_preference: max | web | help | null
status: started | completed | handed_to_operator | abandoned
started_at: timestamptz
completed_at: timestamptz | null
updated_at: timestamptz
```

- Уникальность активной записи: `max_user_id` + `status in (started, completed)`, либо обеспечить upsert в коде.
- В записи не хранить свободный текст пользователя и ПДн.
- Callback payload содержит только код шага/варианта, не персональные значения.
- Все изменения — в audit log с источником `max_bot`.

### 5.2 Создание дела и переход

1. По нажатию «Кабинет на сайте» / `/cabinet` найти либо создать клиента, связанного с `max_user_id`.
2. Найти открытое дело этого клиента; при отсутствии создать `case_id` со статусом `intake`.
3. Связать `case_id` с `max_intake`.
4. Передать `case_id` в deep-link **веб-кабинета** (`CABINET_PUBLIC_URL`).
5. В кабинете показать экран согласия до upload; до принятия согласия endpoint загрузки обязан вернуть отказ.
6. При конфликте привязки `max_user_id` вернуть безопасную ошибку и предложить помощь оператора; не объединять клиентов автоматически.

Использовать единый `/api/portal/*` контур. Legacy `/api/cases/*` и `/api/documents/upload` не расширять.

### 5.3 Оператор и amoCRM

Ветка «Позвать специалиста» должна:

1. завершать либо приостанавливать `max_intake` статусом `handed_to_operator`;
2. создать или обновить лид в amoCRM без документов и лишних ПДн;
3. передать: `max_user_id`, выбранную цель, ответы диагностики, `case_id` (если создан), URL диалога/технический идентификатор;
4. создать задачу оператору «Продолжить диалог MAX»;
5. отправить клиенту: «Передали запрос специалисту. Ответим в этом чате».

Конкретные поля и pipeline amoCRM должны соответствовать ТЗ-12. Если нужных полей нет, добавить их миграцией конфигурации и отразить в документации.

## 8. Безопасность и доступность

- Файлы только через кабинет (private Storage после согласия). Если клиент прислал вложение **в чат** — не сохранять и направить в раздел «Мои документы». Не отдавать публичные ссылки на хранилище.
- Не логировать текст сообщений и callback целиком, если они могут содержать ПДн.
- Webhook: HTTPS, проверка секрета, лимит повторов и идемпотентность update.
- Тексты: короткие предложения, крупные смысловые кнопки, без англицизмов и аббревиатур без расшифровки.
- Везде видна фраза: «Решение принимает СФР».

## 9. Приёмка

### Автотесты

- `/start` показывает целевое меню и не создаёт дело.
- Каждый ответ сохраняет только допустимое enum-значение.
- Повторный `/start` сохраняет незавершённый intake.
- После завершения создаётся ровно один `case_id`; повторное нажатие не плодит дела.
- Deep-link содержит текущий `case_id`.
- Upload через MAX-чат в production отклоняется (`action=upload_rejected_unified_chat`) + CTA «Мои документы».
- Неверный/просроченный `initData` не получает доступ к `/api/portal`.
- Ветка оператора создаёт один upsert-лид и одну активную задачу.

### Ручной E2E

1. Открыть сайт на телефоне → CTA → личный чат; канал и mini-app не предложены раньше диагностики.
2. Пройти «Проверить стаж» с тремя ответами → открыть mini-app → принять согласие → загрузить тестовый PDF → увидеть файл и статус.
3. Пройти тот же путь с «С компьютера» → открыть веб-кабинет → убедиться в том же `case_id`.
4. На любом шаге выбрать «Позвать специалиста» → получить подтверждение в чате и задачу в amoCRM.
5. Отправить вложение в чат production-боту → файл не сохранён, бот объясняет безопасный маршрут и даёт CTA «Мои документы».
6. Вернуться `/start` до и после завершения → корректное продолжение либо меню текущего дела.

## 10. Критерии готовности

- Все обязательные CTA сайта ведут в личный чат MAX.
- Клиент проходит диагностику максимум за три вопроса и получает ясный следующий шаг.
- Документы нигде не проходят через чат.
- MAX, mini-app и веб-кабинет используют одно дело и одну историю статусов.
- Оператор получает контекст без повторного опроса клиента.
- Автотесты, mypy, ruff и ручной E2E из §9 проходят.
- Обновлены пользовательская инструкция MAX и QA-чеклист ТЗ-09.
