# Воронка amo: чеклисты и автоматизация

**Для кого:** оператор, владелец воронки, агент AMO.  
**Связь:** [playbook-operator-amo-card.md](playbook-operator-amo-card.md) · [sales-pipeline-amocrm.md](sales-pipeline-amocrm.md) · ТЗ-19 отзывы · [`playbook-sales-clarity-funnel.md`](../marketing-sales/playbook-sales-clarity-funnel.md) · [`playbook-sales-qualification.md`](../marketing-sales/playbook-sales-qualification.md)

## Правило

SFRFR — истина по делу и документам. amo — продажи, задачи, LOSS, контроль отзыва.  
В amo **нет** сканов, СНИЛС, ИЛС, OCR, Storage URL.

Продукт: **ясность и план**, не надежда на прибавку. Первый оффер — диагностика 3 000 ₽; шаги 5k/8k — после выдачи диагностики.  
В каждой карточке: **следующий шаг + дата + ответственный**.

Позиция подачи: готовим документы и план — подаёте через СФР/МФЦ/Госуслуги вы сами; решение принимает только СФР.

## SLA

| Событие | Цель |
|---------|------|
| Первый контакт после «Новый лид» | в рабочие часы `/kontakty/` — целево **30–60 мин**; иначе в тот же день / следующий рабочий |
| Ответ на сообщение клиента | ≤ 1 рабочего дня |
| Напоминание про документы после оплаты диагностики | ≤ 2 рабочих дней |
| Подтверждение клиенту после оплаты | **≤ 15 минут** в рабочие часы (иначе сразу при выходе) |
| Диагностика после полного комплекта в кабинете | **3 рабочих дня** (§4в; менять только решением владельца) |
| Просьба отзыва после `completed` | 1 авто (MAX) + ≤1 ручное ≥3 дня (ТЗ-19) |

## Маппинг SFRFR → этап amo

Код: `src/sfrfr/integrations/amocrm/pipeline_stages.py` · sync подставляет `status_id` при обновлении сделки (не откатывает на «Новый лид»).

| Сигнал SFRFR | Этап amo |
|--------------|----------|
| создание лида / `pipeline=intake` (create) | Новый лид |
| `b2c=diagnostic_paid` или task `paid:diagnostic*` | Диагностика оплачена |
| `b2c=service_paid` или task `paid:` (сопровождение) | Сопровождение оплачено |
| `b2c=package_delivered` | Пакет выдан |
| `b2c=awaiting_client_submission` / `result_pending` | Клиент подал в СФР |
| `b2c=result_confirmed` | Результат подтверждён |
| `b2c=closed` | Закрыто успешно |
| `pipeline=documents_received` … `extracted` | Документы в кабинете |
| `pipeline=audited` / `draft_ready` / `human_review` | Диагностика выдана |
| `pipeline=completed` или task `review_ask` | Отзыв запрошен |

Ручные этапы (Связались, Квалифицирован, офферы, Отзыв получен) двигает оператор + чеклист.

## Чеклисты-задачи по этапам

Текст задачи — без файлов и без ПДн документов.

### 1. Новый лид → Связались
- [ ] `CONSENT` и канал связи
- [ ] Открыть `SFRFR_CASE_URL`
- [ ] Первый контакт ≤ SLA
- [ ] Перенести в «Связались»

### 2. Квалификация
- [ ] Скрипт `playbook-sales-clarity-funnel.md` / `playbook-sales-qualification.md`
- [ ] `PROBLEM_TYPE` / сегмент (приоритет: родственник → предпенсия → проблемный кейс)
- [ ] Перечень документов статусами (карточка)
- [ ] Поля: следующий шаг, дата следующего шага, ответственный
- [ ] → «Квалифицирован»

### 3. Оффер диагностики
- [ ] Только диагностика **3 000 ₽** (не «комплекс» и не сопровождение первым)
- [ ] Есть **триггер** оффера (§4б): непонятная ИЛС / пропуск / расхождение / отказ СФР / север·архив / родственник — иначе чек-лист
- [ ] Цена с сайта; канон фразы (§4); без гарантии перерасчёта; без «всего лишь»
- [ ] Выбор: «оформляем диагностику или чек-лист?» — не «будете покупать?»
- [ ] После озвучивания цены — дать клиенту ответить (не оправдываться, не скидывать)
- [ ] На «подумаю» — §4б (семья / документы / польза / доверие), не «думайте»
- [ ] Ссылку на оплату — **только после** явного согласия на услугу и цену
- [ ] После «да»: шаблоны подтверждение → оплата → кабинет (`diagnosis-offer-to-payment.md`); сотрудник проверяет черновик
- [ ] На «дорого»/«нет денег» — §5/§5б: чек-лист как **первый шаг**; тег `self-service-checklist`; статус **Ожидаем ИЛС** (не LOSS)
- [ ] Задачи: напоминание №1 на **6-й** день + №2 на **12–14** дн.; черновик → подтверждение сотрудником (§5в)
- [ ] Заметка: даты чек-листа / №1 / №2 · причина ожидания · «не беспокоить»
- [ ] На ответ / возврат — §5г: один вопрос о препятствии; подэтап микроворонки в заметке; дата next contact
- [ ] После №2 без ответа — архив / можно вернуться; не писать без нового обращения
- [ ] Канон подачи; ссылка в кабинет
- [ ] Не принимать сканы в чат/amo
- [ ] Самопроверка: результат за 3 000 понятен? цена прямо? next step + дата?
- [ ] → «Диагностика предложена»

### 4. После оплаты диагностики
- [ ] Этап «Диагностика оплачена» (авто из SFRFR)
- [ ] **≤ 15 мин:** шаблон подтверждения (§4в / `diagnosis-result-delivery.md`) — кабинет, не сканы в чат
- [ ] Задача: дожать ИЛС / трудовую / согласие (только статусы)
- [ ] После полного комплекта — назвать срок **3 рабочих дня**; при неполном — что ещё нужно
- [ ] → «Документы в кабинете» когда базовый пакет в кабинете

### 5. Документы в кабинете
- [ ] Сверка перечня; подтвердить клиенту «комплект получен, срок до [дата]»
- [ ] Флаг тяжёлого Word при необходимости
- [ ] Работа эксперта: заполнить шаблон `diagnosis-stazh-report.md` → PDF (`build_diagnosis_report_pdf.py`)
- [ ] Сложность A–D в шапке PDF; для C/D — второй глаз + срок до обещания клиенту

### 6. Диагностика выдана
- [ ] PDF загружен в кабинет (`doc_type=diagnosis_report`) — **обязательно**
- [ ] QA-чеклист из [playbook-diagnosis-result-standard.md](../marketing-sales/playbook-diagnosis-result-standard.md)
- [ ] Сообщение MAX: готовность + ссылка + CTA `Нужен следующий шаг`
- [ ] Клиент подтвердил получение (или зафиксирована отправка)
- [ ] Предложить шаг 2 (5 000) / шаг 3 (8 000) **только если есть объём** — иначе «достаточно плана»
- [ ] Самопроверка §4в + «понятен без звонка?»
- [ ] Зафиксировать next step + дату

### 7. Сопровождение
- [ ] Оффер тарифа → «Сопровождение предложено» (состав до цены; цена 5k или 8k по объёму)
- [ ] Оплата → авто «Сопровождение оплачено»
- [ ] Выдача пакета → «Пакет выдан»

### 8. Подача и результат
- [ ] Напомнить: подаёте вы сами
- [ ] «Клиент подал в СФР» со слов клиента
- [ ] «Результат подтверждён» без сумм пенсии в публичных полях

### 9. Отзыв (ТЗ-19)
- [ ] Авто-просьба MAX после `completed` → этап «Отзыв запрошен»
- [ ] Ручное напоминание ≥3 дня, не чаще 1 раза
- [ ] Отказ / молчание после напоминания — стоп; при отзыве → «Отзыв получен» → «Закрыто успешно»
- [ ] Журнал без ФИО в git

### C. LOSS
- [ ] Заполнен `LOSS_REASON` из канон-списка
- [ ] Комментарий без ПДн
- [ ] Перенос в системный отказ

### D. Владелец воронки (неделя)
- [ ] Конверсия этап→этап
- [ ] Топ `LOSS_REASON`
- [ ] Доля сделок с `CASE_ID` + живой ссылкой
- [ ] Доля «Отзыв запрошен» после пакета / результата

## Критерии готовности

- Оператор знает следующий шаг на каждом этапе без Storage в amo.
- Есть путь до «Отзыв получен» / «Закрыто успешно» и LOSS с причиной.
- Авто: задача на новый лид; sync колонки на ключевых событиях; отзыв отражается этапом.
- 0 инцидентов «скан/СНИЛС в amo».
